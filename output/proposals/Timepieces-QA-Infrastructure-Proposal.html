1. Bypass Cloudflare Turnstile to stop flaky test runs

The problem

When CI runs against staging.timepieces-d2c.example, the GitHub-hosted runner is served a Cloudflare “Verify you are human” challenge. The runner uses a datacenter IP and headless Chrome — the two strongest bot signals — so Cloudflare interposes its challenge before the app ever loads. Every downstream step then fails with “element not visible,” which looks like flaky locators but is not: the application is simply never reached.

We have already tried evasion. The driver setup masks the most obvious webdriver fingerprints (--disable-blink-features=AutomationControlled, excludeSwitches, Firefox dom.webdriver.enabled=false). It is not enough — a determined managed challenge still blocks. Evasion is an arms race we will keep losing. The reliable fix is an explicit allowlist for our own automation.

The proposal — a secret-header WAF “skip” rule

The test browser sends a secret HTTP header on every request. A Cloudflare WAF rule skips the bot challenge only for requests carrying that header. This is an allowlist for our own traffic against non-production environments — not challenge-solving.

Step A — Cloudflare configuration (Cloudflare admin)

  1. In Security → Events, filter by host staging.timepieces-d2c.example to confirm which service issues the challenge (Super Bot Fight Mode vs WAF Managed Challenge). This decides the exact “skip” target.
  2. Create a WAF custom rule (Security → WAF → Custom rules), placed at the top: 
    # Expression
(http.host in {"staging.timepieces-d2c.example" "dev.timepieces-world.example"})
and any(http.request.headers["x-automation-bypass"][*] == "<SECRET>")

# Action: Skip  →  Super Bot Fight Mode (+ "All managed rules" if applicable)
  3. Scope to non-production only. Optionally also require the GitHub Actions IP ranges (ip.src in {…}) as defence-in-depth.

Plan note: exception rules require Super Bot Fight Mode (Pro+). On free Bot Fight Mode there are no exceptions — then either upgrade, disable BFM on the test host, or use a self-hosted runner with an allowlisted IP (fallback).

Step B — Test framework (send the header)

Inject the header via Chrome DevTools Protocol right after the Chromium driver is created in DriverFactory.initDriver(). It is a no-op when the secret is unset, so local runs are unaffected.

private static void applyCloudflareBypassHeader(WebDriver driver) {
  String token = System.getenv("CF_BYPASS_TOKEN");
  if (token == null || token.isBlank() || !(driver instanceof HasDevTools)) return;
  DevTools dt = ((HasDevTools) driver).getDevTools();
  dt.createSession();
  dt.send(Network.enable(Optional.empty(), Optional.empty(), Optional.empty()));
  dt.send(Network.setExtraHTTPHeaders(new Headers(Map.of("X-Automation-Bypass", token))));
}

Chromium only (Chrome/Edge/Brave). Firefox would need a proxy; since CI defaults to Chrome this covers it.

Step C — CI workflow

# .github/workflows/test-pipeline.yml — Execute step env
CF_BYPASS_TOKEN: ${{ secrets.CF_BYPASS_TOKEN }}
Why this matters: Until this lands, no CI run against staging can pass — the whole pipeline is red for an environmental reason, which erodes trust in the suite and hides real regressions. This single rule restores a reliable signal without weakening protection for real visitors.

2. Whitelisted test user accounts

Automated tests need deterministic, disposable identities. Using real or ad-hoc accounts makes tests slow, flaky, and dangerous (real SMS costs, real charges, dirty state). We propose four purpose-built, server-whitelisted accounts.

AccountPurposeWhat it verifiesSpecial handling
OTP-bypass user
qa+otp@…		 Log in without a real SMS one-time code Auth, session, all logged-in journeys Backend accepts a fixed OTP (e.g. 000000) for this account only
Ephemeral onboarding user
qa+new@…		 Always a brand-new user Sign-up, onboarding, profile creation, empty-state pages Account & data auto-deleted/reset before or after each run
Standard user
qa+user@…		 Established account with normal data Catalog, cart, order history, returning-user flows Stable seeded data; not reset
Payment user
qa+pay@…		 Exercise checkout & payment Cart → pay → confirmation, receipts, payment states Gateway test mode + test cards; payments always succeed

Why each account is required

  • OTP-bypass — Real OTP delivery depends on an SMS provider: it is slow, costs money per message, and is the single biggest source of auth-test flakiness. A fixed code for one whitelisted account removes that dependency while keeping the real flow intact for everyone else.
  • Ephemeral onboarding — Onboarding, “complete your profile,” and empty-state screens can only be tested from a truly fresh account. If the account persists, the second run sees a returning user and the test silently stops covering onboarding. Auto-deletion guarantees a clean slate every time (idempotent tests).
  • Standard user — Returning-user journeys (saved data, order history) need stable, seeded data that is not reset, so assertions are predictable run to run.
  • Payment user — Lets us verify the full money path continuously without real charges or chargebacks (see below). Payment regressions are the most expensive to ship; this makes them catchable nightly.
Payment testing — do it safely. Use the payment gateway’s test/sandbox mode with official test cards, where any test card succeeds regardless of amount — so “real-looking price values” still complete deterministically with zero real money moving. Only if a true production-gateway smoke is required, use a dedicated live test account with a minimal amount and an automatic refund step, and exclude it from revenue analytics (Proposal 3). Never run payment tests against real customer-facing revenue reporting.

3. Exclude test accounts from production analytics

Once the accounts in Proposal 2 run nightly across prod and staging, they will generate hundreds of sessions, sign-ups, add-to-carts, and purchases. If those land in the production analytics at dashboard.timepieces-world.example/dashboard, they corrupt the numbers the business depends on.

What this dashboard is. dashboard.timepieces-world.example/dashboard is the existing production analytics & admin console. It records real customer actions and traffic source/origin, and stores customer names, emails, and watch-purchase history — and it is wired to the backend with the ability to edit live website data. It is a completely separate system from the test dashboard (dev.timepieces-world.example). Because it holds PII and can mutate production, keeping synthetic test identities out of it is both a data-quality and a data-integrity concern.

The proposal

  • Tag at the source. Flag the test accounts/sessions with a durable marker — a user property is_test = true, and/or a request header/cookie the framework sets (it already sets X-Automation-Bypass from Proposal 1, which can double as the analytics signal).
  • Filter in the pipeline. Drop or segment those events at ingestion, or apply a default exclusion filter on every production report/segment in the analytics tool.
  • Keep a QA segment (optional). Route test events to a separate “QA” view so we can still confirm tests fired, without touching real KPIs.
Why this matters: This console drives product and business decisions — conversion, funnel drop-off, revenue, DAU/MAU — and is also where staff view real customers. Nightly bots that sign up, add to cart, and “pay” would inject fake customers (with fake names/emails) and fake purchase records into that real dataset, inflate traffic, fabricate conversions, and distort revenue — leading to wrong decisions, noisy alerts, and test data sitting next to real PII. Proposals 2 and 3 must ship together: a test account is only safe once it is also invisible to this dashboard.

4. Scheduled testing (cron) & the QA_TRIGGER_TOKEN

DevNoNoDevs choose (mostly smoke)Build verification

Cron setup (GitHub Actions)

Cron is in UTC — convert to IST (UTC +5:30) when reasoning about local time. Use github.event.schedule to pick the environment/suite per schedule line.

on:
  schedule:
    - cron: '30 19 * * *'   # 01:00 IST — STAGING smoke+regression
    - cron: '30 20 * * *'   # 02:00 IST — PROD smoke+regression
  pull_request:            # STAGING on every PR (existing)
  workflow_dispatch:        # DEV / manual (devs choose env, tags)

jobs:
  test:
    steps:
      - name: Resolve target
        run: |
          if [ "${{ github.event.schedule }}" = "30 20 * * *" ]; then
            echo "ENV=prod"    >> $GITHUB_ENV; echo "TAGS=@Smoke or @Regression" >> $GITHUB_ENV
          elif [ "${{ github.event.schedule }}" = "30 19 * * *" ]; then
            echo "ENV=staging" >> $GITHUB_ENV; echo "TAGS=@Smoke or @Regression" >> $GITHUB_ENV
          fi

Why the dev team must add QA_TRIGGER_TOKEN

The most valuable trigger is “run QA after every deploy.” That trigger originates in the product application repo (or the deploy job) and must start a workflow in the qa-automation repo. This is a cross-repository trigger, and GitHub deliberately does not allow it with the default token:

  • The built-in secrets.GITHUB_TOKEN is scoped to its own repository only. It cannot dispatch workflows in another repo, and events it raises cannot start further workflow runs (GitHub’s loop-prevention).
  • Therefore the product repo needs a dedicated token — QA_TRIGGER_TOKEN — a PAT (fine-grained: Actions: Read & write on qa-automation) stored in that repo’s GitHub Secrets.
# product repo → after a successful deploy → trigger QA
curl -X POST \
  -H "Authorization: Bearer ${{ secrets.QA_TRIGGER_TOKEN }}" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/TimepiecesTech/qa-automation/dispatches \
  -d '{"event_type":"run-smoke-tests"}'
Why this matters: Without QA_TRIGGER_TOKEN, post-deploy and dashboard-initiated runs fail silently with 401/403 — “the tests just didn’t trigger.” A dedicated, least-privilege, revocable token makes every job’s trigger authenticated, reliable, and auditable, and is the same mechanism the hosted dashboard uses to launch runs.

5. Future dashboard features (after hosting at dev.timepieces-world.example)

Once the test dashboard is hosted, we can make it genuinely useful to non-technical stakeholders, not just engineers. Three additions:

(a) One-click runs for non-technical stakeholders

Prominent, role-gated “Run Smoke” / “Run Regression” buttons with a confirmation step. Behind the scenes this is the dispatch mechanism the dashboard already uses (Proposals 1 & 4). Add lightweight roles so stakeholders can run and read without seeing engineering controls.

(b) LLM explanation of results in plain language

After a run, the backend sends the structured results (Allure/JSON summary — counts, failed scenarios, error snippets) to Claude (Anthropic API) and returns a short, non-technical summary cached per run. Recommended models: Claude Haiku 4.5 for cheap high-volume summaries, or Claude Sonnet 4.6 for richer narratives. Example output: “18 of 20 checks passed. Checkout failed on Safari because the payment button didn’t appear — likely a layout issue on that browser.”

Keep it read-only and grounded: feed only the run’s own results, label it AI-generated, and link to the underlying Allure report.

(c) Run configuration: execution mode & browser/platform matrix

  • Execution mode — Parallel / Sequential / Batch, mapped to TestNG thread settings (e.g. -Dthreads, suite parallel).
  • Browser/platform matrix — “Chrome only”, “Chrome + Safari”, “macOS only”, etc., expressed as a GitHub Actions matrix.
Safari/macOS needs the right runner. Safari only runs on macOS. To offer “Chrome + Safari” or “mac only”, use GitHub-hosted macOS runners or a cloud grid (e.g. BrowserStack/Sauce Labs/Selenium Grid). Worth scoping cost before enabling broad matrices from the UI.

(d) Cross-navigation to the analytics dashboard (future)

A button to move between the test dashboard (dev.timepieces-world.example) and the production analytics console (dashboard.timepieces-world.example/dashboard), and back. The two stay separate systems — the link is for convenience only.

Guard the crossing. Because dashboard.timepieces-world.example exposes customer PII and can edit live website data, the navigation link must respect each system’s own authentication/roles — landing on the analytics console must not inherit test-dashboard access. Keep dev.timepieces-world.example read-only with respect to production: it shows test analytics and Allure reports, it does not write to the product backend.
