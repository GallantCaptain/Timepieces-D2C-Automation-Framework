Cross-Browser Testing

Running the same scenarios on Chrome, Firefox and Edge — sequentially or in parallel.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. Two supported shapes

ShapeHowWhen
Sequential (one JVM per browser)Run mvn test three times with different -Dbrowser, letting Allure results accumulate into one report.The simple, always-safe default. Exactly what docker/entrypoint.sh does.
Parallel (one JVM, all browsers at once)The testng-crossbrowser.xml suite on the Grid (DEC-0014).When you want all three concurrently and have the Grid up.

2. Sequential — the safe default

.\mvnw.cmd clean test "-Dexecution.mode=GRID" "-Dbrowser=chrome"  "-Denv=production"
.\mvnw.cmd test       "-Dexecution.mode=GRID" "-Dbrowser=firefox" "-Denv=production"
.\mvnw.cmd test       "-Dexecution.mode=GRID" "-Dbrowser=edge"    "-Denv=production"
.\mvnw.cmd allure:report   # one merged report across all three

Each invocation is a clean JVM with one browser, so there is no shared state to race on. Local runs work the same way with execution.mode=local, provided the browser is installed.

3. Parallel in one JVM (DEC-0014)

testng-crossbrowser.xml runs chrome, firefox and edge concurrently with parallel="tests", one <test> block per browser:

docker compose --profile grid up -d
.\mvnw.cmd test "-Dsurefire.suite=testng-crossbrowser.xml" "-Dexecution.mode=GRID" "-Denv=production"

How the browser reaches the driver

The browser normally comes from -Dbrowser, a JVM-global system property. Three <test> blocks writing it would race — last writer wins, and all three would silently run the same browser while the report claimed otherwise. The suite avoids this with a per-thread override:

// DriverFactory
private static final ThreadLocal<String> tlBrowserOverride = new ThreadLocal<>();
// resolveBrowser() prefers the thread-local, else falls back to ConfigReader.get("browser")

// BaseRunner @BeforeMethod reads the suite's <parameter name="browser"> and pins it
DriverFactory.setBrowserForThread(browser);   // @AfterMethod clears it

Why @BeforeMethod, not @BeforeTest Under a parallel DataProvider the scenarios execute on pool threads, not the thread that ran @BeforeTest. TestNG runs @BeforeMethod on the same thread as its @Test, so the pin is set on the thread that will actually build the driver. This was verified empirically before the code was written.

4. Verifying it was REALLY cross-browser

Never trust a green run alone The failure mode here is a silent wrong answer: a green report that quietly used one browser three times. Ask the Grid instead — each node serves only its own browser:

docker compose --profile grid logs selenium-node-chrome  | Select-String "Session created"
docker compose --profile grid logs selenium-node-firefox | Select-String "Session created"
docker compose --profile grid logs selenium-node-edge    | Select-String "Session created"

Three roughly-equal non-zero counts = genuine cross-browser. A zero anywhere means that browser never ran, whatever the report says. The Allure environment page should likewise list Browser.CHROME, Browser.FIREFOX and Browser.EDGE.

5. Browser substitutions (logged, never silent)

RequestedActually usedWhy
chrome / firefox / edgeas-isReal nodes / local installs exist.
bravechromeBrave is Chromium; the difference (shields, branding) is not exercised by these tests. Logged.
safarisafari.fallback.browserReal Safari only on macOS (ADR-0008); elsewhere a configured Chromium fallback, annotated in the report.

Thread budget 3 test blocks × data-provider-thread-count=2 = up to 6 concurrent browsers, matching the Grid's 3 nodes × 2 sessions = 6 slots. Asking for more than the Grid can serve makes sessions queue and time out — and a starved browser looks exactly like a flaky app. Add node replicas for more throughput, not more threads.
