Locator Strategies

How elements are found, why data-testid is preferred, and the traps that caused real failures.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. The locator hierarchy

Locators are chosen in this order of preference — earlier is more stable:

RankStrategyExampleUse when
1data-testidmain[data-testid='home-main']Almost always. Purpose-built for automation; survives copy/style changes.
2stable attribute (name, href, id, role)a[href='/accessories/all']No testid exists but a semantic attribute is stable.
3text anchor (XPath normalize-space)//h3[normalize-space()='Contact details']Third-party UI (Razorpay) with neither testid nor stable attribute.
4structural / positional...following::input[position()<=4]Last resort; marked VERIFY-tier in comments because it is brittle.

The rollout A repo-wide data-testid rollout replaced brittle CSS/text selectors across the page objects specifically to kill flaky tests. When the app adds a testid, prefer it and retire the older locator.

2. Where locators live

Locators are private final By fields on the page/component object, never inline in step definitions. Business methods and verifications reference the fields, so a UI change is a one-line edit in one place. Provenance for third-party locators (e.g. Razorpay's real testids, captured live) is documented in docs/scrape-artifacts/.

3. Finding elements safely — the BasePage helpers

HelperWhat it doesWhy it exists
waitForVisibility(By)Wait until present and visible.Presence ≠ visibility; asserting on a present-but-hidden node is a classic false pass/fail.
waitForFirstVisible(By)Return the first visible match, preferring in-viewport.Responsive pages render hidden desktop/mobile twins that share a selector — see §4.
isEventuallyDisplayed / isEventuallyHiddenWait for a state to settle.Assertions must wait for state, not sample it mid-transition.
clickElement(By)Scroll to centre, native click, JS-click fallback.Overlays and off-screen elements intercept naive clicks.

4. Traps that caused real failures

Hidden responsive twins A selector shared by a desktop and a mobile variant matches two nodes, only one visible. clickElement takes the first in DOM order — often the hidden one — so the click "succeeds" but nothing happens, and the next assertion fails on the wrong page. Fix: waitForFirstVisible(...).click(). This bit the sidebar Accessories link and several accessory PDPs.

Presence vs visibility on teardown Some third-party overlays (Razorpay) hide without removing their DOM nodes. A presence check (findElements(...).isEmpty()) reports the modal as still open forever. Use a visibility check (isEventuallyHidden) when asserting something has gone.

Overlays intercept clicks The cookie bar, drop cards and the cart drawer sit over other controls. BasePage.open() runs SiteOverlayHandler.dismissBlockingOverlays(); a control behind an auto-opened drawer needs the drawer closed first (an explicit step), not a forced click.

Selector typos fail loudly, later A malformed selector (e.g. a stray ]) throws InvalidSelectorException on first use — which reads like a driver fault, not a typo. Validate new selectors against the live DOM before wiring them in.

5. Healable locators

When Healenium is enabled (off by default), the driver is wrapped so that a locator which no longer matches can be self-healed from previously-seen node attributes. That is a safety net, not a substitute for good locators — see the Healenium guide.
