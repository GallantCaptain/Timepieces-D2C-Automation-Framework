OKF — Organizational Knowledge Framework for Agentic Engineering

The project's durable memory: how it is structured, and how it lets AI agents build the framework across sessions.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. What the OKF is

The Organizational Knowledge Framework (docs/okf/) is the authoritative, living memory of the project — the single place that answers "why is it like this, what is done, what is broken, and what was decided." It is not narrative documentation; it is a set of structured, cross-referenced registers designed to be read and written by both humans and AI agents.

Why it matters for handover Code tells you what; git tells you when. The OKF is the only place that records why — the decisions, the dead ends, the constraints that are not derivable from the source. For a new SDET (or a new agent), it is the fastest path to context.

3. Traceability IDs — the connective tissue

Every meaningful thing has a stable ID, and entries cross-reference each other so a claim can always be traced to evidence:

PrefixRegisterExample use
REQ-RequirementsA capability the suite must verify.
TASK-BacklogA unit of work.
DEC- / ADRDecisionsAn architectural choice + its rationale.
STAT-Status/milestonesA completed, verified achievement.
ISSUE-Known issuesA defect (app-side or framework-side).
RISK-RisksSomething that could go wrong + mitigation.

A decision cites the tasks and issues it resolves; an issue cites the status entry that fixed it. This is what makes the OKF a graph, not a pile of notes.

4. The OKF as an agent harness

This framework was built largely by AI agents (an orchestrator directing capable models) across many sessions. A model's context window is finite and resets between sessions — so the OKF is the externalised, durable memory that lets an agent pick up exactly where the last one left off. In practice:

  • Read on entry. An agent starting work reads CurrentStatus.md, known-issues.md and decisions-log.md to rebuild context no window can hold.
  • Write on exit. Every substantive change appends to changelog.md and updates the relevant register, so the next agent inherits the reasoning, not just the diff.
  • Decisions are load-bearing. When a choice is reversed (e.g. DEC-0014 was deferred then implemented the same day once a verification oracle appeared), the log records both the reversal and the evidence that justified it — so the reasoning is auditable, not lost.
  • Append-only discipline. The changelog is never rewritten. History that can be silently edited cannot be trusted as memory.

Rule for the next maintainer Treat the OKF as you would production code. If you change behaviour, record why in the OKF in the same commit. A fix with no OKF trail is half-done — the next person (or agent) will re-discover the same dead end you just escaped.

5. Governance (DEC-0009 / ADR-0009)

The OKF's authority, structure and append-only rules are themselves an accepted decision. OKF_INDEX.md is the entry point and lists the primary source documents; README.md in docs/okf/ is the navigation hub.
