Dashboard — Customization Guide

How to change the flows, charts, theming and data the dashboard shows.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. Flows → Cucumber tags

The "run a flow" buttons map flow keys to Cucumber tag expressions in dashboard/server/src/flows.config.ts. This is the first thing to adjust as the suite's tags evolve:

FlowTag expression
Login Flow@Login
Checkout Flow@Checkout
Complete End-to-End Flow@Smoke or @Regression
 
// dashboard/server/src/flows.config.ts — add or edit a flow
{ key: "payment", label: "Payment Flow", tags: "@Payment and @Regression" }

Keep tags real A flow whose tag matches zero scenarios dispatches a run that does nothing. After editing, confirm the tag expression selects what you expect with a local --dry-run-style check.

2. Charts and trends

Trend data comes from GET /api/runs/trends?days=N — daily aggregates over the test_runs table. To add or change a chart in the React SPA (dashboard/web):

  1. Extend the trends query/endpoint if you need a new aggregate (e.g. per-browser pass rate).
  2. Consume it in a web component; the SPA is React + Vite + TypeScript.
  3. Keep the read path auth-gated — every route except login/health requires a JWT.

3. What the dashboard is meant to show (planned scope)

The intended shape, per the dashboard requirements, is a stakeholder-facing view with:

  • Trends — pass rate and volume over time.
  • On-demand flows — trigger predefined runs and watch live status.
  • Execution history — per-run results linking to the published Allure reports.
  • Auth-gated access — email/password, so it can be shared without exposing raw pipelines.

Hosting (at dev.timepieces-world.example) is out of the framework's scope and handled separately.

4. Theming and branding

  • The SPA is a standard Vite React app — global styles and a theme layer live in dashboard/web/src. Adjust tokens/variables there rather than per-component for a consistent restyle.
  • Keep charts legible in both a projector/boardroom setting and a laptop — trends are the headline artefact for non-technical stakeholders.

5. Data contract — don't break the publisher

The table is shared The dashboard reads the exact test_runs table the Java TestMetricsPublisher writes. If you change the schema for a new chart, update both the publisher (writer) and the dashboard (reader) together, or one side will silently break. The publisher already tolerates the DB being absent (it logs and moves on), so a schema mismatch will not fail tests — it will just produce wrong or empty charts, which is harder to notice.

6. Where it will grow next

The natural next features — and where a new owner would extend — are per-flow drill-downs, flaky-test surfacing (tie into the invocation-count analysis), and richer filters (env × browser × tag). All of these are additive over the existing /api/runs* surface.
