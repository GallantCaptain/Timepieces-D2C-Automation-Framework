Configuration (Properties) Reader

How ConfigReader resolves every setting across CLI, environment and property files.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. What ConfigReader is

com.timepieces.automation.utils.ConfigReader is the single entry point for every tunable value in the framework — base URLs, timeouts, browser, execution mode, feature flags, secrets. Page objects and utilities never read System.getProperty directly; they call ConfigReader.get("some.key") so that the resolution rules are applied consistently in one place.

2. The three-tier precedence ladder

get(key) returns the first source that has the key, in this order:

TierSourceExampleWins over
1JVM system property (-D on the command line)-Dbrowser=firefoxeverything
2OS environment variableCF_BYPASS_TOKENthe properties file
3the env properties file (+ optional local override)staging.propertiesnothing (base layer)
 
// simplified from ConfigReader.get(key)
String v = System.getProperty(key);       // tier 1
if (v != null) return v.trim();
v = System.getenv(key);                    // tier 2
if (v != null) return v.trim();
return prop.getProperty(key);              // tier 3 (may be null → logged as unmapped)

Design intent The command line is the operator's voice and must win. This is why ADR-0005 fixes this precedence, and why BaseRunner was fixed (ISSUE-020) to stop the suite XML silently overriding -Denv.

3. Which properties file is loaded

On first use, ConfigReader reads -Denv (default staging) and loads, from the test classpath:

config/<env>.properties            # committed base config
config/<env>.local.properties      # OPTIONAL, gitignored — layered on top if present

The local override is where machine-specific secrets go (staging password, pilot phone) without touching committed files. Keys in the local file replace keys in the base file.

One environment per JVM The loaded config is cached once per JVM in a static block, keyed on the -Denv seen at class-load time. You cannot switch environments mid-run; start a new Maven invocation for a different -Denv.

5. Behaviour to know

  • Trimming. Every returned value is trim()-ed, so trailing whitespace in a properties file never bites.
  • Unmapped keys. A key found in no tier returns null and logs a WARN ("Configuration key lookup requested but returned empty/unmapped"). These warnings are normal for optional keys — they are not errors.
  • Missing base file is fatal. If config/<env>.properties is not on the classpath, initialisation throws — a typo in -Denv fails fast rather than silently testing the wrong place.
  • Secrets never defaulted. pilot.phone has no fallback: a test that needs it throws with a message naming the key, instead of quietly using someone's real number.

6. Adding a new setting

  1. Add the key to both staging.properties and production.properties (keep them in step so neither can silently disagree — the lesson of ISSUE-005).
  2. Read it via ConfigReader.get("your.key"); never System.getProperty directly.
  3. If it is a secret, leave it blank in the committed file and document the local-override / env-var path.
