DataProvider vs Invocation Count — Deterministic vs Probabilistic

Two different reasons to run a test more than once, and which knob to reach for.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. The distinction in one line

A DataProvider runs a test once per data row, in parallel — that is deterministic coverage. An invocation count runs the same test many times to expose flakiness — that is probabilistic sampling.

2. DataProvider — parallel, deterministic coverage

The framework's parallelism comes from a TestNG @DataProvider(parallel = true). In BDD, BaseRunner overrides Cucumber's scenario provider so every scenario becomes one parallel data row:

@Override
@DataProvider(parallel = true)
public Object[][] scenarios() {
    return super.scenarios();   // one row per Cucumber scenario, run concurrently
}

Because DriverFactory holds the WebDriver in a ThreadLocal, each parallel row gets its own isolated browser. The number of concurrent browsers is the data-provider thread count:

.\mvnw.cmd test "-Ddataproviderthreadcount=4"   # 4 scenarios (4 browsers) at once
.\mvnw.cmd test "-Ddataproviderthreadcount=1"   # fully serial — best for debugging

The TDD search tests use the same pattern with a named provider:

@DataProvider(name = "keywordData", parallel = true)   // one row per search keyword

Deterministic Given the same data, a DataProvider run covers exactly the same set of cases every time. It answers "does each case pass?" — not "is this case stable?"

3. Invocation count — repetition, probabilistic sampling

Some questions can only be answered by running the same case repeatedly: is this keyword's ranking stable? does this flow flake 1 in 20 times? A single pass cannot tell you; you have to sample.

In this framework that repetition is driven at the suite level by scripts/run-search-api-analysis.ps1, which invokes the search suites a configurable number of times and aggregates every run:

output/search-api-analysis/<timestamp>/
    keyword-aggregation.csv     # per-keyword pass/fail across all runs
    summary.md                  # headline stability findings
    runs/det-run-1.log ...      # each individual invocation

The exploratory search test exists precisely for this: it de-duplicates keywords and samples them repeatedly to surface non-deterministic relevance behaviour that a single deterministic pass would miss. That is how the search-fallback defects (ISSUE-009…012) were characterised — not from one run, but from the distribution across many.

Probabilistic A repeated run answers "how often does this pass?". One green pass proves a case can pass; it does not prove it is stable. Flakiness is a frequency, and you need samples to measure a frequency.

4. Choosing the knob

You want to know…Reach forWhy
Does every scenario / keyword pass?DataProvider (the normal run)One row per case, run once, in parallel.
Is this flow flaky?Repeat the suite (analysis script)Flakiness is a rate; measure it over many runs.
Is a search result stable week to week?Exploratory suite × N via the scriptSamples the distribution, not a point.
Faster feedback on a big suite?Raise dataproviderthreadcountMore browsers concurrently — coverage, not repetition.

Don't confuse the two Raising the thread count does not make results more reliable — it just runs the same single-pass coverage faster. Reliability evidence comes only from repetition. And repetition without isolation (shared login numbers, shared cart) manufactures false flakiness — which is why repeated auth runs must vary identities and stay within OTP cooldowns.
