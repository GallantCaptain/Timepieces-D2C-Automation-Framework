Architecture Decision Records (ADRs)

Every accepted architectural decision, its rationale, and where it lives.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. How decisions are recorded

Formal decisions live as numbered ADRs under docs/adr/; docs/okf/decisions-log.md is the index and also holds decisions captured inline (DEC-####) where a full ADR was not warranted. Each carries a status, the decision, the rationale, and traceability IDs.

DEC-0014Deferred, then implemented and verified the same day. Parallel cross-browser in one JVM. Rollback is deleting one file.

4. The DEC-0014 story — why it is the model to follow

Decisions can reverse — on evidence DEC-0014 was first deferred because its worst outcome was a silent wrong answer (a green report that secretly ran one browser three times), which could not be verified before handover. Building the Grid changed the calculus: each node serves only its own browser, so per-node session counts prove cross-browser actually happened. With a way to verify, the risk dropped from "unacceptable" to "moderate and testable," and it was implemented additively (unset behaviour is byte-identical) with a one-file rollback. The log records the deferral, the reversal, and the evidence — which is exactly how a decision record should behave.

5. Writing a new ADR

  1. Copy the format of an existing file in docs/adr/ (context → decision → alternatives → consequences → status).
  2. Add a row to decisions-log.md with the ID, status, decision, owner and traceability.
  3. Cross-reference the tasks/issues it resolves so the OKF graph stays connected.
