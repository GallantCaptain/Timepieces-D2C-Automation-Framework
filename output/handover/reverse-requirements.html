1. Why "reverse" requirements

Timepieces did not hand over a complete written specification. Much of what the suite verifies was reverse-engineered from the live product and from behaviour confirmed with the product owner — then written down so coverage is auditable. This document is that recovered specification plus a Requirements Traceability Matrix (RTM) linking each requirement to the tests that exercise it.

Two requirement sources Forward requirements (from the PRD — see guide 20) and reverse requirements (recovered here) together define the coverage contract. Where they conflict, the live product's confirmed behaviour wins and the discrepancy is filed as an ISSUE.

3. How to keep the RTM honest

  • Every new .feature or TDD class should map to a REQ (recovered or PRD). If it maps to none, the requirement is missing — write it.
  • When a requirement is only partially automated (e.g. a third-party or gated step), say so in the Notes column and tag the scenario @Manual — never leave a gap looking covered.
  • When the product's real behaviour contradicts a requirement, the requirement stands and the gap becomes an ISSUE; the RTM row points at both.

Coverage ≠ green A row can be "verified by" a test that currently fails by design (a privacy probe, a bruteforce probe) — because the requirement is correct behaviour and the test asserts it. Those failures are findings, not regressions.
