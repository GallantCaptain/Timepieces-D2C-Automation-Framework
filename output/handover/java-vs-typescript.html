Java vs TypeScript — in this project

The two language implementations of the same framework, and what changes between them.

Framework: Java 25 · Selenium 4.44 · Cucumber 7 · TestNG 7 · Updated 23 Jul 2026

1. Same architecture, two languages

The Playwright POC (automation-ts/) is a deliberate 1:1 port of the Java framework's structure, so the design ideas transfer even though the syntax does not:

There is also a Python port A separate Playwright-Python port exists outside this repo (d2c-automation-python) as a third language surface of the same design. Same page-object model, pytest instead of TestNG/cucumber-js.

2. The fluent page object — where the languages differ most

Java uses the CRTP (curiously recurring template pattern) so an inherited open() returns the concrete page type without every page overriding it:

// Java: self-type generic
public abstract class BasePage<SELF extends BasePage<SELF>> {
    public SELF open() { ...; return self(); }   // returns the concrete subtype
}
public class HomePage extends StoreFrontBasePage<HomePage> { ... }
// TypeScript: polymorphic `this` gives the same fluent typing for free
class BasePage {
  async open(): Promise<this> { ...; return this; }   // `this` is the concrete subtype
}

TypeScript's polymorphic this expresses in one keyword what Java needs a recursive generic bound to achieve. Same fluent ergonomics, far less ceremony.

3. Config resolution

  • Java: ConfigReader — -D > env var > <env>.properties, cached once per JVM.
  • TypeScript: ConfigReader.ts — process.env > .env file > defaults, the same three-tier idea using Node conventions.

4. Async is the pervasive difference

Everything is a Promise In TypeScript every interaction is async/await. A missing await is the #1 porting bug — the line "passes" because it returns a pending promise instead of doing the work. Java's calls are synchronous, so this class of error does not exist there. Enable @typescript-eslint/no-floating-promises to catch it.

6. Practical guidance for the next SDET

  • Extend the Java framework for real coverage work — it is the production surface.
  • Treat automation-ts/ as a reference for what a Playwright migration would look like; keep its structure mirroring the Java side so the comparison stays honest.
  • When porting a page object, port the locators and business methods verbatim first, then adapt waits (Playwright auto-waits — delete most explicit waits) and add await everywhere.
